Claude Code 源码深度解读

第一章：背景与概述

1.1 泄漏事件始末

2026 年 3 月 31 日，安全研究员 Chaofan Shou（@Fried_rice）发现 Anthropic 在发布 Claude Code npm 包时，将一个 .map（Source Map）文件意外暴露在公网可访问的 R2 存储桶中。Source Map 是 JavaScript 构建工具生成的调试文件，其中包含从编译产物到原始 TypeScript 源代码的完整映射——这意味着任何人都可以通过这个文件还原出 Claude Code 的全部未混淆源码。

该事件迅速在开发者社区扩散。warren-wupeng/claude-code 仓库是对这批源码的公开存档，附带了一个由仓库作者额外添加的 MCP 服务器（mcp-server/），使任何 MCP 兼容工具（VS Code Copilot、Claude Desktop 等）都可以将此源码作为知识库进行探索。

这不是一个玩具项目。从代码量和工程复杂度看，这是一个经过数十人多年迭代、投入大量工程资源的生产级系统。

第二章：宏观架构

2.1 五层架构模型

Claude Code 的代码组织遵循清晰的分层设计：

┌─────────────────────────────────────────────────────┐ │ 入口层 (Entrypoints) │ │ cli.tsx · init.ts · sdk/ · mcp.ts │ ├─────────────────────────────────────────────────────┤ │ 核心引擎层 (Core Engine) │ │ QueryEngine.ts · query.ts · context.ts │ ├─────────────────────────────────────────────────────┤ │ 工具与命令层 (Tools & Commands) │ │ tools/ (41个) · commands/ (~50个) · Tool.ts │ ├─────────────────────────────────────────────────────┤ │ 服务层 (Services) │ │ compact/ · permissions/ · mcp/ · bridge/ · tasks/ │ ├─────────────────────────────────────────────────────┤ │ UI 层 (Terminal UI) │ │ components/ (~140个) · ink/ · screens/ │ └─────────────────────────────────────────────────────┘

2.2 目录结构与职责

目录 职责 关键文件
src/entrypoints/ 多入口启动逻辑 cli.tsx, sdk/, mcp.ts
src/query/ LLM 调用核心 QueryEngine.ts, context.ts
src/tools/ 工具实现 (41个) BashTool, FileEditTool, etc.
src/services/ 基础设施服务 permissions/, mcp/, bridge/
src/components/ Terminal UI 组件 Messages.tsx, PromptInput.tsx

设计原则：每一层只依赖下层，避免循环依赖。工具层可以调用服务层，但服务层不能直接调用具体工具。

第三章：核心引擎——QueryEngine

3.1 LLM 调用的核心循环

QueryEngine 是整个系统的心脏，负责协调 LLM 调用、工具执行和上下文管理：

用户输入 ▼ QueryEngine.submitMessage()（消息入队） │ ├── context.ts（并行组装 system prompt） │ ├── git status / log │ ├── CLAUDE.md 文件（所有父目录） │ └── MEMORY.md（持久记忆） │ ├── query.ts（调用 Anthropic API，流式） │ └── 工具调用循环 ├── Tool.checkPermissions() ├── permissions.ts（全局权限决策） ├── Pre-tool hooks ├── Tool.call()（执行工具） ├── Post-tool hooks └── 追加 tool_result，继续循环 │ ▼ SDKMessage 流（yield 给 UI / SDK 消费者）

3.2 上下文压缩策略

Claude Code 实现了多层级的上下文管理：

  • 智能截断：优先保留最近的工具调用和结果
  • 摘要压缩：使用 LLM 生成历史对话摘要
  • 记忆外置：将长期信息写入 MEMORY.md
  • 动态加载：根据当前任务动态选择相关上下文

3.3 CLAUDE.md 记忆系统

系统会递归搜索当前目录及所有父目录的 CLAUDE.md 文件，将其内容注入到 system prompt 中。这形成了一个分层的项目配置系统：

~/projects/my-app/CLAUDE.md           # 项目特定配置
~/projects/CLAUDE.md                  # 项目组通用配置
~/CLAUDE.md                          # 个人全局配置

每个层级的配置都会被包含，形成完整的上下文。

第四章：工具系统

4.1 工具接口设计

所有工具都实现统一的 Tool<Input, Output> 接口：

interface Tool<TInput, TOutput> {
  name: string
  inputSchema: ZodSchema<TInput>
  outputSchema: ZodSchema<TOutput>

  call(input: TInput, context: ToolUseContext): Promise<TOutput>
  checkPermissions(input: TInput, context: ToolUseContext): PermissionResult
  isEnabled(): boolean
  isConcurrencySafe(): boolean
  isReadOnly(): boolean
}

这种设计的优势：

  • 类型安全：输入输出都有严格的 Zod schema 验证
  • 权限隔离：每个工具独立检查权限
  • 并发控制：明确标识哪些工具可以并发执行
  • 功能标识：区分只读工具和修改性工具

4.2 权限系统的双门控

Claude Code 实现了工具级 + 全局级的双层权限控制：

  1. 工具级权限：每个工具的 checkPermissions() 方法
  2. 全局权限：permissions.ts 的统一决策引擎

权限决策流程：

用户调用工具 → 工具.checkPermissions() → 全局 permissions.ts → 执行决策

4.3 41个工具的分类

类别 工具名 主要功能
文件操作 FileReadTool, FileWriteTool, FileEditTool 基础文件 CRUD
系统交互 BashTool, PowerShellTool 命令行执行
代码搜索 GrepTool, GlobTool 文本搜索和文件匹配
协作功能 AgentTool, BriefTool 多 Agent 协调
开发工具 LSPTool, NotebookEditTool IDE 集成和 Jupyter 支持

每个工具都是独立的模块，可以单独测试、独立部署。

第五章：多Agent协作——Swarm

5.1 进程隔离模型

Claude Code 通过 Swarm 实现多 Agent 协作，每个子 Agent 在独立进程中运行：

主进程 (Main Agent) │ ├── 子进程 A（专业Agent：前端开发） ├── 子进程 B（专业Agent：后端API） └── 子进程 C（专业Agent：数据分析） 每个子进程： - 独立的内存空间 - 独立的工具权限 - 独立的上下文管理

5.2 Mailbox 通信机制

进程间通信通过"信箱"模式实现：

  • 发送消息：Agent A 写入共享的消息队列
  • 接收消息：Agent B 轮询读取自己的信箱
  • 消息格式：标准化的 JSON 格式
  • 持久化：消息存储在文件系统中，支持崩溃恢复

5.3 任务状态机

每个 Agent 任务都有明确的状态流转：

pending → running → completed
   │         │         │
   │         └─→ failed │
   └─────────────────→ cancelled

状态变化会触发相应的事件回调，支持复杂的工作流编排。

第六章：工程化亮点

6.1 Feature Flag 构建系统

Claude Code 使用 Bun 的 feature flag 实现条件编译：

// 只有启用 PROACTIVE 特性时才编译这部分代码
const SleepTool = feature('PROACTIVE')
  ? require('./tools/SleepTool.js').SleepTool
  : null

优势：

  • Dead Code Elimination：未启用的功能完全不会打包
  • 渐进发布：新功能可以逐步开放给不同用户群体
  • A/B 测试：支持实验性功能的灰度发布

6.2 启动优化

系统采用多项技术优化启动速度：

  • 懒加载：工具和服务按需加载
  • 并行初始化：上下文组装和权限检查并发执行
  • 缓存机制：频繁访问的配置和元数据缓存在内存中
  • 预编译：TypeScript 编译结果缓存

6.3 TypeScript 类型系统亮点

代码中有一些精妙的 TypeScript 类型设计：

// 条件类型保留字面量类型
type BuiltTool<D> = {
  [K in keyof (D & TOOL_DEFAULTS)]:
    (D & TOOL_DEFAULTS)[K] extends infer V
      ? V extends boolean
        ? V
        : V extends string
        ? V
        : (D & TOOL_DEFAULTS)[K]
      : never
}

buildTool() 的返回类型是 BuiltTool<D>，用条件类型在 D 和 TOOL_DEFAULTS 的展开上保留了每个字段的字面量类型，而不是退化为宽泛的 boolean 或 string。这使得 isConcurrencySafe: true 在类型层面是 true 而非 boolean，下游代码可以依赖这个精确信息。

第七章：总结与启示

7.1 对 AI Agent 架构设计的启示

读完这份代码，有几个判断值得记下来。

异步生成器是 Agent 流式输出的正确抽象。 AsyncGenerator<SDKMessage> 比回调、比事件发射器、比 Promise 链都干净。调用方用 for await...of 消费，可以随时 break 中断，背压（backpressure）天然处理。zoey-ai 目前的 WebSocket 透传方案更底层，如果未来重构可以考虑在服务层引入这个模式。

工具系统的关键是接口统一而非实现统一。 41 个工具行为各异，但都实现同一个 Tool<Input, Output> 接口。QueryEngine 不需要知道 BashTool 怎么执行命令，只需要知道它有 call()、checkPermissions()、renderToolUseMessage()。这是真正的开闭原则——新增工具不修改引擎。

7.2 权限系统值得借鉴之处

Claude Code 的权限架构是这份代码里工程完成度最高的部分，有两点特别值得学习。

双层门控而非单一检查点。 工具级 + 全局级权限让系统既灵活又安全。工具可以基于输入内容做精细判断（比如 BashTool 检查命令是否包含 rm -rf），全局层面可以做统一的策略控制（比如生产环境禁止所有文件写入）。

权限即代码，而非配置。 每个权限检查都是 TypeScript 函数，可以单元测试、可以版本控制、可以 code review。相比基于 YAML 或 JSON 的权限配置，代码形式的权限更容易维护和调试。

7.3 最后的判断

这份代码回答了一个重要问题：一个生产级 AI Agent 系统的复杂度应该在哪里？

答案是：复杂度应该在架构和工程上，而不是在算法和模型上。Claude Code 没有自研 LLM，没有复杂的 RAG 算法，没有花哨的 prompt engineering。它的价值在于把"AI 调用工具"这件事做到了工程化、产品化、企业化。

51.2 万行代码，大部分都在解决这些"无聊"的工程问题：权限管理、错误处理、并发控制、状态管理、UI 渲染、性能优化。但正是这些"无聊"的代码，构成了一个真正可用的 AI 工具产品。

这或许就是 AI 工程化的本质：不是让 AI 更聪明，而是让 AI 更可靠。
